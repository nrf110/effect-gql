Effect GraphQL automatically converts Effect Schema definitions to GraphQL types. This page documents how each Schema type maps to its GraphQL equivalent.

## Primitive Types

| Effect Schema | GraphQL Type | Notes |
|--------------|--------------|-------|
| `S.String` | `GraphQLString` | Required struct fields are non-null; root/computed fields remain nullable |
| `S.Number` | `GraphQLFloat` | Use `S.Int` for `GraphQLInt` |
| `S.Boolean` | `GraphQLBoolean` | |
| `S.BigInt` | Falls back to `GraphQLString` | No automatic bigint serialization; expose an explicit string instead |
| `S.Date` | Falls back to `GraphQLString` | No automatic ISO serialization; expose an explicit ISO string instead |

### Examples

```typescript
import * as S from "effect/Schema"

// String field
S.Struct({ name: S.String })
// → name: String!

// Number field
S.Struct({ age: S.Number })
// → age: Float!

// Boolean field
S.Struct({ active: S.Boolean })
// → active: Boolean!
```

## Nullability

These types describe **fields inside a struct** (and corresponding required
argument keys), not registered query, mutation, subscription, or computed fields.
Those registered fields are nullable even when their schema is `S.String` or
`S.Array(...)`: for example, `hello: String` and `users: [User]`.

| Effect Schema | GraphQL Type |
|--------------|--------------|
| `S.String` | `String!` (non-null) |
| `S.NullOr(S.String)` | `String` (nullable) |
| `S.optional(S.String)` | `String` (nullable) |
| `S.UndefinedOr(S.String)` | `String` (nullable) |

### Examples

```typescript
S.Struct({
  required: S.String,              // → required: String!
  nullable: S.NullOr(S.String),    // → nullable: String
  optional: S.optional(S.String)   // → optional: String
})
```

<Aside type="note">
GraphQL doesn't distinguish between `null` and `undefined`. Both `NullOr` and `optional` map to nullable GraphQL fields.
</Aside>

## Arrays

| Effect Schema | GraphQL Type |
|--------------|--------------|
| `S.Array(S.String)` | `[String]!` |
| `S.NullOr(S.Array(S.String))` | `[String]` |
| `S.Array(S.NullOr(S.String))` | `[String]!` |

### Examples

```typescript
S.Struct({
  // Required list; GraphQL still permits null elements
  tags: S.Array(S.String),
  // → tags: [String]!

  // Nullable list, also with nullable elements
  categories: S.NullOr(S.Array(S.String)),
  // → categories: [String]

  // Required list with explicitly nullable element schema
  aliases: S.Array(S.NullOr(S.String))
  // → aliases: [String]!
})
```

Tuples also map to homogeneous GraphQL lists, not positional GraphQL types. The first fixed element determines the list item type; the rest element is used only when there are no fixed elements. For example, `S.TupleWithRest(S.Tuple([S.Number]), [S.Int])` maps to a list of `Float`, preserving the valid value `[1.5, 2]` for both output and input. Effect Schema still validates the fixed and rest positions when decoding resolver arguments.

For tuples with required elements after a variadic segment, input restoration
uses each trailing schema at its position relative to the end of the list.
Hidden tags and Options are restored with that position's schema before full
Effect decoding; missing positions and invalid trailing values are still rejected.

## Structs (Object Types)

`S.Struct` maps to GraphQL Object types:

```typescript
const UserSchema = S.Struct({
  id: S.String,
  name: S.String,
  email: S.String,
  age: S.optional(S.Number)
})

GraphQLSchemaBuilder.empty.objectType({ name: "User", schema: UserSchema })

// With this explicit registration:
// type User {
//   id: String!
//   name: String!
//   email: String!
//   age: Float
// }
```

### Nested Structs

```typescript
const AddressSchema = S.Struct({
  street: S.String,
  city: S.String
})

const UserSchema = S.Struct({
  id: S.String,
  address: AddressSchema
})

GraphQLSchemaBuilder.empty
  .objectType({ name: "Address", schema: AddressSchema })
  .objectType({ name: "User", schema: UserSchema })

// With both types explicitly registered:
// type Address {
//   street: String!
//   city: String!
// }
//
// type User {
//   id: String!
//   address: Address!
// }
```

Plain struct variable names are not runtime schema metadata. Register an explicit
name as above or use a schema identifier annotation. Unregistered plain structs
receive generated names such as `Object_<suffix>`; `objectType({ schema })`
requires an explicit name unless the schema carries an inferred name.

## Tagged Types

Tagged types provide automatic type name inference:

### TaggedStruct

```typescript
const UserSchema = S.TaggedStruct("User", {
  id: S.String,
  name: S.String
})

objectType({ schema: UserSchema })  // Name "User" is inferred
```

### TaggedClass

```typescript
class User extends S.TaggedClass<User>()("User", {
  id: S.String,
  name: S.String
}) {}

objectType({ schema: User })  // Name "User" is inferred
```

### Class

```typescript
class User extends S.Class<User>("User")({
  id: S.String,
  name: S.String
}) {}

objectType({ schema: User })  // Name "User" is inferred
```

## Enums

### String Literals

```typescript
const StatusSchema = S.Literals(["ACTIVE", "INACTIVE", "PENDING"])

// Register as enum:
enumType({
  name: "Status",
  values: ["ACTIVE", "INACTIVE", "PENDING"]
})
```

For input arguments, a literal union matches a registered enum only when its non-null literal values exactly match that enum's values. For example, registering `Status` with `["ACTIVE", "INACTIVE"]` maps `S.Literals(["ACTIVE", "INACTIVE"])` to `Status`, including nullable and optional forms. A different union such as `S.Literals(["ACTIVE", "PENDING"])` falls back to `String`, even though it shares `ACTIVE` with `Status`. Clients send `"PENDING"` as a string; Effect Schema still validates the original literal union before passing the decoded value to the resolver. The same matching applies inside arrays and to the encoded side of transformations.

Unmatched multi-member input unions use the automatic converter's first-member fallback without looking up that member as an enum. This also applies to mixed unions: `S.Union([S.Literal("ACTIVE"), S.Number])` falls back to `String`, not a registered enum containing `ACTIVE`. Effect Schema still validates the original union after GraphQL input coercion.

### Using S.Enum

```typescript
enum Status {
  ACTIVE = "ACTIVE",
  INACTIVE = "INACTIVE"
}

const StatusSchema = S.Enum(Status)

// Register as enum:
enumType({
  name: "Status",
  values: Object.values(Status)
})
```

## Unions

### Tagged Unions

```typescript
const CatSchema = S.TaggedStruct("Cat", {
  meows: S.Boolean
})

const DogSchema = S.TaggedStruct("Dog", {
  barks: S.Boolean
})

const PetSchema = S.Union([CatSchema, DogSchema])

// Register types and union:
objectType({ schema: CatSchema })
objectType({ schema: DogSchema })
unionType({
  name: "Pet",
  types: ["Cat", "Dog"],
  resolveType: (value) => value._tag  // Uses the tag
})
```

## Input Types

For input types (arguments), mapping uses the encoded representation of
transformations. Schemas with an inferred metadata name append `Input`: a tagged
`User` produces `User` for output and `UserInput` for input. Unnamed plain structs
receive generated input names, not names derived from their JavaScript variables.
An explicit `inputType({ name, schema })` registration takes precedence.

```typescript
// The encoded input is a string; the decoded argument is a Date.
query("events", {
  type: S.Array(S.String), // Explicit ISO strings for output
  args: S.Struct({ after: S.DateFromString }),
  resolve: ({ after }) => Effect.succeed([after.toISOString()]),
})
```

### Input Object Types

Complex input structures:

```typescript
const CreateUserInputSchema = S.Struct({
  name: S.String,
  email: S.String,
  role: S.optional(S.Literals(["ADMIN", "USER"]))
})

inputType({
  name: "CreateUserInput",
  schema: CreateUserInputSchema
})

mutation("createUser", {
  type: UserSchema,
  args: S.Struct({
    input: CreateUserInputSchema
  }),
  resolve: ({ input }) => { ... }
})
```

### Composing Low-Level Helpers

The configuration-free helpers `toGraphQLType`, `toGraphQLInputType`, and `toGraphQLArgs` reuse GraphQL types by directional schema identity, so repeated conversions compose without changing inferred names:

```typescript
import { toGraphQLType, toGraphQLInputType, toGraphQLObjectType, toGraphQLArgs } from "@effect-gql/core"

const User = S.TaggedStruct("User", { id: S.String })
const output = toGraphQLType(User)       // User
const input = toGraphQLInputType(User)   // UserInput
const firstArgs = toGraphQLArgs(S.Struct({ user: User }))
const secondArgs = toGraphQLArgs(S.Struct({ user: User }))
// Both argument maps reuse UserInput and can be composed in one GraphQL schema.

const A = toGraphQLObjectType("A", S.Struct({ user: User }))
const B = toGraphQLObjectType("B", S.Struct({ user: User }))
// Nested types are scoped to their explicit root: A_User and B_User.
```

Only configuration-free conversions share their input/output caches. Each `toGraphQLObjectType` call owns its conversion state and additional fields; its configured GraphQL type is never shared globally. Explicit root names remain unchanged and scope their nested names, so independently configured helpers can coexist without leaking computed fields. Recursive references reuse one type within their conversion graph. Use the schema builder when registered names and computed fields should apply throughout the schema.

## Transformations

Effect Schema transformations are handled differently for input vs output:

### Output Types (Query/Field Results)

Mapping follows the decoded type, but resolver results are **not generally run
through the schema's encoder**. In particular, `S.DateFromString` does not promise
ISO output and `S.BigIntFromString` does not serialize bigint results automatically.
Return an explicit GraphQL-compatible representation:

```typescript
query("now", {
  type: S.String,
  resolve: () => Effect.sync(() => new Date().toISOString()),
})
// Returns an ISO string, e.g. "2024-01-15T10:30:00.000Z"
```

Top-level Option results receive special handling to expose `None` as `null` and
`Some` as its value. That handling is not a general-purpose output codec encoder,
nor a recursive encoder for every property in returned objects.

### Input Types (Arguments)

Uses the encoded type (what the client sends):

```typescript
// Client sends: { after: "2024-01-15T00:00:00.000Z" }
// Resolver receives: { after: Date object }
```

## Custom Scalars

Transformations are useful for **input decoding**, not for registering a new
GraphQL scalar or automatically serializing custom output values:

```typescript
query("increment", {
  type: S.String,
  args: S.Struct({ value: S.BigIntFromString }),
  resolve: ({ value }) => Effect.succeed((value + 1n).toString()),
})
```

Clients send a string, the resolver receives a bigint, and the resolver explicitly
returns a string. JSON can similarly be accepted with
`S.fromJsonString(S.Unknown)` as an argument decoder. For JSON responses, use a
string output schema and explicit `JSON.stringify`, rather than relying on codec
encoding.

## Type Resolution Order

When building GraphQL types, the schema builder:

1. **Checks registered types first** - Types registered with `objectType()`, `enumType()`, etc.
2. **Falls back to automatic conversion** - If no registered type matches, converts Schema directly

This allows you to customize how specific types are handled:

```typescript
// Register custom handling for UserSchema
objectType({
  name: "User",
  schema: UserSchema,
  description: "A user in the system"
})

// UserSchema now uses the registered type
// instead of automatic conversion
```

Registrations match schema identity, not structural similarity. `S.optionalKey(UserSchema)` changes field nullability without losing the registered object's computed fields, interface identity, or input type. A separate `S.Struct` with the same properties remains a separate type.

Exact schema and original-AST registrations take precedence over directional projection aliases. Distinct transformation wrappers can therefore have separate object, interface, or input registrations even when they share a decoded or encoded representation. Their registered names and computed fields are preserved at root fields and nested references, including optional keys and lists. Use the original registered wrapper when its identity matters: a projection alone cannot distinguish wrappers that share that projection.

This includes separate `X.pipe(S.decodeTo(Y))` wrappers that reuse the same `X` and `Y` schemas and the default transformation. `S.optionalKey`, `S.mutableKey`, and their combinations retain the originating wrapper's registration rather than merging wrappers with shared transformations.

Input key codecs preserve this exact-registration precedence before projecting
to their encoded representation. In particular, `S.OptionFromOptionalKey(codec)`
keeps the input name registered for `codec`. Two registered codecs sharing an
encoded schema still expose their own input names when wrapped this way,
independent of registration order.

Output Option wrappers retain the registration of their original value codec, including when `S.toType(codec)` was registered first under a different name. This applies to object and interface registrations in root and nested fields: `S.Option(codec)`, `S.OptionFromNullOr(codec)`, the undefined/nullish variants, and the optional-key variants select the original codec's registered type and computed fields rather than its projection's registration. Option fields remain nullable; for example, `S.OptionFromNullOr(codec)` exposes `None` as GraphQL `null`.

Output registrations apply only to the decoded representation. Registering an object decoded from a string does not turn unrelated string fields into that object. Input registrations apply to the encoded representation. Recursive input references reuse the registered input object, and inferred output types share one conversion context across registered fields and root operations.

Within a builder, inferred types also share their directional projection identity: using a schema alongside `S.toType(schema)` for outputs, or alongside `S.toEncoded(schema)` for inputs, reuses the corresponding GraphQL type. Projection does not merge unrelated schemas with the same shape or schemas with different annotations, and optional keys retain their field nullability.

## Limitations

Some Schema features don't have direct GraphQL equivalents:

| Effect Schema | Handling |
|--------------|----------|
| `S.Tuple` / `S.TupleWithRest` | Homogeneous list using the first fixed element, or the rest element when no fixed elements exist; loses positional info |
| `S.Record` | Not directly supported |
| `S.ReadonlyMap` / `S.HashMap` | No automatic GraphQL map representation |
| `S.ReadonlySet` / `S.HashSet` | No automatic conversion to GraphQL lists; expose arrays explicitly |
| Refinements | Argument validation runs; most checks do not change SDL (`S.Int` is recognized) |
| Brands | Ignored at GraphQL level |

### Workarounds

An array-to-Record transformation works for **input decoding only**. Its encoded
side is a GraphQL list; the decoded Record is not a valid GraphQL object output.

```typescript
// Accept key-value pairs as input, decode them into a Record.
import * as SchemaGetter from "effect/SchemaGetter"

const MetadataEntries = S.Array(S.Struct({ key: S.String, value: S.String }))
const MetadataInput = MetadataEntries.pipe(
  S.decodeTo(S.Record(S.String, S.String), {
    decode: SchemaGetter.transform((arr) =>
      Object.fromEntries(arr.map(({ key, value }) => [key, value]))),
    encode: SchemaGetter.transform((obj) =>
      Object.entries(obj).map(([key, value]) => ({ key, value }))),
  })
)

// For responses use the actual list schema and convert explicitly.
const metadata: Record<string, string> = { theme: "dark" }
query("metadata", {
  type: MetadataEntries,
  resolve: () => Effect.succeed(
    Object.entries(metadata).map(([key, value]) => ({ key, value }))
  ),
})
```
